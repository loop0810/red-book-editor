## Context

当前服务端已有结构化 SourceExperience、风格 Agent、Agent trace 和事实/审核相关测试，但还没有面向真实模型输出的固定案例集与人工评分记录。评测集将作为后续 Agent 改进的外部质量基线，不改变当前生成链路。

## Goals / Non-Goals

**Goals:**

- 用 5 个真实且脱敏的案例建立第一轮基线。
- 让案例输入、预期边界、模型输出、人工评分和人工修改稿可以关联追溯。
- 允许同一案例重复运行，并支持不同 Agent 版本之间的比较。
- 在现有代码测试之外补充用户视角的内容质量评估。

**Non-Goals:**

- 本阶段不修改 prompt、Agent loop、模型适配器或安全规则。
- 不自动判断人工评分，不引入新的模型供应商或评测平台。
- 不把宝宝照片、原始身份信息或完整敏感 trace 保存到评测资料中。

## Decisions

### 1. 第一轮使用文件化案例和评分记录

先使用仓库内版本化的 Markdown/YAML 或 JSON 评测资料，而不是立即建立数据库评测系统。案例数量较少，文件更容易人工审阅、提交和回滚，也便于后续转成自动化测试输入。

替代方案：直接建立评测数据库。当前案例和运行次数不足以证明数据库的必要性，先不引入额外持久化复杂度。

### 2. 每个案例至少运行两次

两次运行可以初步观察输出稳定性，同时控制真实模型调用成本。评分记录保留每次运行，而不是只保存人工选出的最好结果。

### 3. 评分与硬失败分离

总分用于比较整体质量，事实、安全和未知结果扩写使用硬失败标签单独约束。这样不会出现“文案很漂亮但包含医疗风险，仍然因为总分高而通过”的情况。

### 4. 评测记录只保存必要摘要

模型标识、耗时、输出和 Agent trace 需要用于诊断，但 trace 只保留阶段、工具和短摘要，不保存密钥、完整请求头或不必要的儿童隐私内容。

## Risks / Trade-offs

- [Risk] 5 个案例不能代表所有真实场景 → 先作为第一轮基线，完成后根据失败模式扩充到 10 个或更多。
- [Risk] 人工评分存在主观差异 → 固定评分说明，并为每个低分或硬失败记录一句原因。
- [Risk] 真实模型输出包含敏感内容 → 案例先脱敏，输出和 trace 只保留在受控仓库，禁止提交照片和密钥。
- [Risk] 随机性导致两次运行差异过大 → 记录模型版本和运行参数，后续再决定是否固定 temperature 或增加运行次数。

## Migration Plan

先创建案例、评分说明和运行记录模板，再使用当前真实模型完成 5 个案例的两次运行。基线确认后，后续事实和医疗安全变更必须复跑同一批案例并保留对比结果。
