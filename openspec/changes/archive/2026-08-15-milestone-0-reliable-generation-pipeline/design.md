## Context

当前有两条内容生成入口：Flutter 使用的 `/api/v1/notes/generate` 只返回临时草稿，账号工作台使用的 `/api/v1/accounts/{account_id}/notes` 才负责持久化、加载账号栏目上下文和部分审核。风格 Agent 已支持账号和栏目上下文参数，但主生成入口没有传入这些参数；生成结果和字段重生成也可能在没有审核结果时返回 `ready`。

现有笔记内容使用 JSONB 保存，`style_form` 已经在部分写入路径中出现，但没有贯穿服务端 DTO、更新请求、读取映射和 Flutter 模型。当前数据库结构和跨端模型都已经存在，因此本变更优先修正应用服务和契约，不引入新的 Agent 状态系统或数据库表。

## Goals / Non-Goals

**Goals:**

- 让主生成入口产生可保存、可列表查询、可重新打开的持久化草稿。
- 让不同生成入口共享账号/栏目上下文、生成、审核、状态映射和持久化语义。
- 让 `style_form` 在生成、保存、读取、恢复和字段重生成之间保持一致。
- 让审核结果成为 `ready` 和导出的明确前置条件。
- 让字段重生成只产生目标字段，并由服务端合并到原草稿后重新审核。

**Non-Goals:**

- 不实现 Fact Ledger、Claim Audit、持久化 AgentRun、取消/恢复或流式事件。
- 不引入 RAG、MCP、多 Agent、自动发布或新的模型供应商。
- 不在本变更中重写现有审核规则；只统一调用时机和状态/导出门禁。
- 不要求为 `style_form` 新增独立数据库列；继续使用现有 JSONB 内容并兼容旧记录。

## Decisions

### 1. 使用共享的内容工作流应用服务

新增一个位于内容工作流模块的应用层服务，负责校验账号和栏目上下文、调用生成器或风格 Agent、执行统一审核、计算草稿状态并返回组合结果。FastAPI Router 只负责 HTTP 输入输出和依赖注入，SQLAlchemy 通过 repository/port 适配，不让领域逻辑依赖具体 ORM。

两个现有生成入口暂时保留以避免立即破坏客户端契约，但都调用同一个应用服务。主生成入口在服务成功后创建 `NoteModel` 和第一条 `DraftVersionModel`，返回的 `note_id` 因而可以直接用于保存；账号工作台入口复用相同的上下文和审核流程。

替代方案：直接把一个 Router 调用另一个 Router。这样会继续保留 HTTP 层耦合和重复的错误处理，因此不采用。

### 2. 在生成完成后统一执行审核并集中计算状态

生成、整篇风格重写、字段重生成和保存后的草稿都通过同一个审核入口。服务端集中使用以下状态映射：

- 没有审核结果：不得为 `ready`；对于已形成的草稿进入 `needs_review` 或返回失败。
- 存在 blocking：`needs_review`，导出拒绝并返回风险原因。
- 只有 warning：`needs_review`，返回审核提示；是否允许带提示导出沿用现有 blocking 导出边界，不得静默清除 warning。
- 审核完成且没有 findings：`ready`。

状态计算不能依赖客户端提交的 `status` 或 `review`，也不能通过 `style_form` 是否存在来绕过审核。

替代方案：只在 Router 层补几处 `review_draft` 调用。这样容易遗漏未来入口，因此采用共享服务和单一状态映射函数。

### 3. 将 `style_form` 作为可选的跨端草稿元数据

在 `NoteDraftDto`、Flutter `NoteDraft`、保存请求和读取映射中增加可空的 `style_form`。新生成草稿必须写入该值；整篇重写显式切换表达形式时更新该值；字段重生成未显式传入形式时使用草稿保存的值。

旧数据可能没有该字段。对于旧草稿，若字段重生成请求也没有显式 `form`，服务端返回明确的 `style_form_required` 错误，而不是静默使用错误的默认形式。这样可以兼容旧数据，同时避免隐式改变内容风格。

### 4. 字段重生成使用单字段结构化结果

字段重生成使用目标字段专用的输入和输出结构：标题返回标题候选，正文返回正文，话题返回话题列表，封面文案返回字符串。服务端将结果合并到原草稿，保留其他字段、来源事实、审核上下文和 `style_form`，再对合并后的完整草稿执行审核。

为了保持当前 Flutter API 的兼容性，响应仍可返回完整 `NoteDraft`；“只生成/只更新字段”是服务端任务和合并语义，而不是强制改变当前响应形状。

替代方案：继续生成完整文案后取一个字段。该方式浪费模型调用，也会让未请求字段参与不必要的漂移，因此不采用。

### 5. 使用兼容式持久化，不新增数据库迁移

`style_form` 写入现有 `notes.content` JSONB，并由 `note_dto`、repository 和版本读取统一映射。旧 JSONB 内容缺少该键时读取为 `None`。只有在实现过程中发现 JSONB 无法满足约束时，才另行提出 Alembic migration；本变更默认不改表结构。

### 6. 以端到端链路测试作为完成标准

测试覆盖主生成入口和账号工作台入口，至少验证：生成、保存、列表、重新打开、版本记录、字段重生成、审核状态和导出门禁。客户端测试验证 `style_form` 的 JSON 往返和编辑器在恢复后继续使用该形式。模型真实调用不作为本变更的必需测试条件，使用现有 stub/fake gateway 验证流程，另保留真实模型评测作为后续工作。

## Risks / Trade-offs

- [Risk] 两个旧入口仍然存在，未来可能再次出现语义分叉 → 让两个入口只负责组装请求，核心流程和状态映射全部通过共享应用服务，并增加入口等价性测试。
- [Risk] 旧笔记没有 `style_form` → 读取时允许为空；字段重生成缺少形式时返回明确错误，要求客户端补充选择。
- [Risk] warning 的人工确认流程当前还不完整 → 本变更至少保证 `needs_review` 和提示不被清除；显式确认/审核事件可在后续 Agent Workflow 变更中补充。
- [Risk] 生成后立即持久化会让失败重试涉及数据库事务 → 先完成模型和审核，再在同一事务中写入笔记及版本；失败时不写入伪成功的 `ready` 草稿。
- [Risk] 字段级结构化输出可能受模型格式漂移影响 → 对每个字段使用 Pydantic 校验，并将解析失败转换为可重试的生成错误。

## Migration Plan

1. 先新增共享应用服务、状态映射和契约字段，保留旧接口路径。
2. 将两个生成入口、整篇重写和字段重生成迁移到共享服务。
3. 为主生成入口开启持久化写入，并补齐版本记录和读取映射。
4. 更新 Flutter 模型和 API Client，验证新旧草稿读取兼容性。
5. 运行服务端单元/API/集成测试和 Flutter 分包测试；确认链路稳定后再考虑删除重复的旧实现。

回滚时可以保留新增的可选 `style_form` 字段并恢复旧入口实现；不会执行破坏性数据迁移。已写入的 `style_form` 对旧代码是额外 JSONB 键，不影响旧字段读取。
