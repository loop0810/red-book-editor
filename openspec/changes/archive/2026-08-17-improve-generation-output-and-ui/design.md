## Context

当前生成链路已经具备模型网关、有限 Agent、风格档案、Fact Ledger、Claim Audit 和 AgentRun 生命周期，但这些能力的边界没有保持在服务端内部。客户端把 Agent trace、审核命中和声明证据放进主要编辑页面，导致用户关注“系统怎么做”而不是“文案是否可用”。当前输入模型也以 `SourceExperience` 为中心，缺少明确的内容重心，因此模型可能把限制条件或附属动作写成标题主旨。

现有 `docs/decisions/20260811-agent-pipeline-and-policy-architecture.md` 已经提出“固定安全内核 + 领域策略包 + 有限 Agent”，但代码和跨端契约仍把育儿、Agent trace 和审核快照作为主要产品语义。本设计将该架构落到产品边界：通用生成内核负责内容生成，领域策略包负责领域差异，C 端只接收内容结果和必要的可行动状态。

## Goals / Non-Goals

**Goals:**

- 建立内容优先的 C 端主流程：主题/重心、原始素材、账号上下文和表达风格输入，输出可编辑的小红书内容。
- 让标题和选题角度以用户明确的内容重心为最高优先级，区分主题、事实、观点和限制条件。
- 将育儿领域从通用流程中抽离为第一个可版本化 Domain Strategy Pack，为未来领域扩展预留稳定边界。
- 保留 Agent、事实账本、声明审计、运行诊断和评测作为服务端质量与学习基础，但不把它们泄漏到普通 C 端信息架构。
- 让账号领域、定位、语气和栏目真实参与生成，消除客户端硬编码账号/栏目作为产品上下文的做法。
- 让真实阻断风险继续受到服务端门禁保护，同时避免普通改写和低置信度内部审计产生无关的疾病/用药提示。

**Non-Goals:**

- 本 change 不实现第二个真实业务领域；只定义领域策略包边界并完成 parenting pack 的适配准备。
- 不把 Agent 改造成完全自治、多 Agent 协作或新的模型框架。
- 不接入小红书自动发布、账号登录、互动操作或外部数据抓取。
- 不删除服务端的运行诊断、事实账本、审核快照、版本和发布记录数据；本阶段只调整其产品边界和展示投影。
- 不把所有内部质量结果翻译成复杂的用户解释面板；用户提示以少量、具体、可行动为原则。

## Decisions

### 1. 用通用 ContentBrief 替代育儿专属生成入口

核心输入抽象为：

```text
ContentBrief
├─ focus                 用户明确的内容主题/重心，必填
├─ raw_material          用户原始素材，必填
├─ domain_context        当前领域的可选结构化补充
└─ asset_ids             可选图片素材
```

`focus` 是标题和选题角度的最高优先级；`raw_material` 是事实来源；`domain_context` 只补充领域所需信息。育儿的宝宝月龄、照护场景等字段进入 `domain_context`，而不是成为所有未来领域必须理解的 `SourceExperience` 字段。

替代方案是继续保留 `SourceExperience` 作为通用输入，只增加一个 `topic` 字段。该方案短期改动较小，但会继续把育儿字段传播到 API、客户端和 Agent，无法真正支持未来领域，因此不作为长期边界。迁移期间可以保留旧字段兼容读取，由育儿适配器将旧结构转换为 `ContentBrief`。

### 2. 采用 Domain Strategy Pack，而不是每个领域一个独立 Agent

领域策略包提供以下版本化能力：

```text
DomainStrategyPack
├─ domain_id / version / display_name
├─ supplemental_input_schema
├─ generation_context
├─ quality_rules
├─ safety_policy
├─ allowed_tools
└─ user_facing_issue_projection
```

通用 Content Agent 只负责理解输入、组织内容角度、生成结构化草稿、调用质量检查和修订。它不直接判断“这是育儿还是旅游”，也不包含领域专属的医疗、金融或法律分支。领域策略包由服务端加载、校验和授权工具，避免模型自行改变系统安全边界。

### 3. 把用户结果和内部诊断分成两个投影

内部工作流可以产生比用户结果更多的信息：

```text
Agent Run
├─ internal diagnostics
├─ trace
├─ fact ledger
├─ claim audit
├─ policy findings
└─ user result projection
    ├─ title_candidates
    ├─ body
    ├─ hashtags
    ├─ cover_copy (optional)
    ├─ image_suggestions
    └─ actionable_issue (only when needed)
```

API 内部可以继续保存和传递诊断，但普通客户端的响应模型不应因为复用内部 DTO 而携带并展示这些字段。开发和评测通过日志、评测记录或授权调试接口读取 trace；产品页面只渲染 `user result projection`。

替代方案是保留现有 `StyledNoteResponse.draft + agent_trace` 并在 Flutter 中折叠。该方案仍会把学习型信息放在用户流程中，且后续很难保证所有内部字段不被继续添加到页面，因此不采用。

### 4. 主题重心由用户显式提供，模型负责组织而不是猜测

生成提示和最终校验必须把 `focus` 作为独立输入，并明确：

- 标题候选、topic angle 和正文开头优先表达 `focus`；
- 原始素材中的限制、取舍和“不做什么”默认是支持信息，不得自动成为标题主语；
- 只有当用户明确把限制条件写进 focus 时，限制条件才可以成为主标题角度；
- 领域策略和账号定位约束风格与范围，但不能覆盖用户本次内容主题。

这比单纯修改标题 Prompt 更可靠，因为 focus 会进入 API 契约、事实账本、评测输入和标题质量测试。

### 5. 安全门禁继续内部强制，但用户提示按实际风险投影

服务端仍然必须阻止真实的诊断、用药方案、危险建议、虚构关键经历和其他领域策略定义的 blocking 结果。改变的是结果语义：

- `supported`、`uncertain`、`unsupported` 是内部审计状态，不是默认用户文案；
- 低置信度或自然语言改写不能仅因逐字匹配失败就产生用户错误；
- 用户提示必须携带实际风险类别和目标字段，不能使用固定的“疾病/用药”总括文案；
- 普通无风险内容不显示任何医疗或审核提示；
- 服务端可以拒绝导出，但客户端只显示足以让用户修改的最小信息。

### 6. 首要 C 端流程保持小而完整，复杂能力降级为次级入口

首次生成结果的默认页面只包含标题、正文、话题、配图建议、必要的封面文案、编辑、复制、保存和重新生成。版本历史、Diff、字段候选历史、发布记录、素材库复杂管理和 Agent 运行可视化保留后端能力，但不在首次结果中展开。

这不是删除学习能力，而是把学习能力放到正确的位置：服务端和评测系统用于理解 Agent，用户页面用于完成内容创作。

### 7. 账号上下文由服务端解析，客户端不硬编码运行时标识

账号配置至少包含 `domain_id`、定位、语气和边界；生成时客户端选择当前账号和启用栏目，服务端解析真实账号/栏目实体与领域策略。客户端不再把随机生成的栏目 ID 写进源代码，也不把账号设置页做成只修改本地 controller 的演示页面。

迁移期间可以保留一个本地开发账号作为默认选择，但其 ID 和栏目必须来自账号/栏目查询或初始化数据，不允许通过常量绕过上下文解析。

### 8. 首次使用先配置工作台，不在本 change 引入登录系统

当前产品是单用户本地工作台，缺少账号配置不应把首页变成不可操作的错误页。账号 API 增加不带客户端 UUID 的创建入口，由服务端生成账号标识；客户端在首次配置成功后创建一个默认内容栏目，再重新读取账号和栏目列表。

没有账号时显示“配置第一个账号”按钮；账号存在但没有启用栏目时显示“创建默认栏目”按钮。页面明确说明当前版本不需要登录，避免用户误以为存在一个尚未实现的注册入口。注册、登录、密码、会话和多用户权限留给独立的身份 change。

### 9. 模型配置错误必须可诊断，不能静默降级

真实运行默认使用 DeepSeek；只有明确配置 `MODEL_PROVIDER=stub` 时才允许离线 stub。
服务端从 `server/.env` 和当前工作目录兼容读取本地配置，因此从仓库根目录启动和从
`server/` 目录启动的行为一致。缺少 `DEEPSEEK_API_KEY` 时，健康检查返回
`model_configured=false`，异步 AgentRun 标记为模型错误，客户端显示可行动的配置提示，
而不是把失败包装成无意义的 Dart 异常类名或伪造生成成功。

## Risks / Trade-offs

- [Risk] 通用 `ContentBrief` 会增加旧育儿数据和 API 兼容成本 → 保留旧 `SourceExperience` 的读取适配器，在服务端边界转换，不让旧字段继续扩散到新的通用接口。
- [Risk] Domain Strategy Pack 过早抽象会产生空泛配置 → 只实现 parenting 的最小有效 pack，要求每个字段和规则都能对应一个生成或校验场景，不提前做通用插件市场。
- [Risk] 隐藏审核细节可能让用户不理解为什么不能复制 → 提供少量精确的用户问题投影，并保留内部 request ID/调试信息，避免把完整审计结构搬回 C 端。
- [Risk] 放宽 warning/uncertain 对 `ready` 的影响可能降低内容质量 → blocking 门禁仍由服务端强制，增加围绕主题重心、来源外关键经历和实际高风险建议的评测案例；普通自然改写不再被低质量文本匹配误伤。
- [Risk] 保留版本、发布和候选能力会继续诱使 UI 扩张 → 将“主流程默认可见”和“次级/内部能力”写入契约与验收测试，新增 C 端字段必须说明其用户价值。
- [Risk] 账号配置与栏目初始化迁移期间存在旧客户端固定 ID → 提供真实账号/栏目查询或开发初始化流程，先保证客户端拿到有效实体，再移除常量。

## Migration Plan

1. 先同步本 change 的 specs、跨端契约、产品说明和 Agent 架构决策，冻结内容优先边界。
2. 增加 `ContentBrief`、`domain_id` 和用户结果投影的兼容契约；旧 `SourceExperience` 由 parenting adapter 转换。
3. 抽出通用 Content Agent 上下文和 Domain Strategy Pack 端口，先接入 parenting pack；保持现有模型网关和 Agent Runtime 可复用。
4. 将真实生成、保存、审核和导出路径统一到新的内容简报与用户结果投影，修复 focus 优先级和自然改写审计。
5. Flutter 先改输入页面和结果页面，移除 trace/审计/运行阶段主展示，接入真实账号和栏目选择。
6. 用代表性案例验证：普通周岁宴记录不得出现医疗提示；标题必须围绕用户 focus；医疗高风险案例仍被阻断；配图建议继续返回。
7. 稳定后再决定版本历史、字段候选和发布复盘是否作为次级页面恢复；如新契约破坏旧客户端，保留向后兼容读取并逐步弃用旧字段。

## Open Questions

- Domain Strategy Pack 的配置格式第一版可以先使用服务端版本化文件，后续是否需要数据库可编辑策略不影响本 change 的核心边界。
- `cover_copy` 是否继续作为默认结果字段可以在客户端原型验证后调整，不影响标题、正文、话题和配图建议的核心输出。
